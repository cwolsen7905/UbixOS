UbixOS Virtual Memory Manager (VMM)
====================================

Source: sys/vmm/


1. Memory Layout
----------------

Each process has a private 4 GB virtual address space divided into three regions:

  0x00000000 - 0x000FFFFF  (first 1 MB)
    Shared read-only region mapped identically (1:1) across all processes.
    Contains BIOS data, video frame buffers, and the kernel boot code.

  0x00100000 - 0xBFFFFFFF  (1 MB to 3 GB)
    Per-process region. Available for the task's code, data, heap, and stack.
    This address range is private; each process has its own page tables here.

  0xC0000000 - 0xFFFFFFFF  (top 1 GB)
    Kernel-only region. Shared read-only mapping across all processes, but
    only accessible at ring 0 (i.e., while executing a syscall). User-space
    code that attempts to access this region triggers a general protection fault.

At physical address 0x00100000 each process stores its own page directory.
PDE entry 0x300 (page 0x768) is the self-referencing slot that points to the
page tables covering the top 1 GB kernel mapping.


2. Functions
------------

vmmInit()
  Top-level initialization entry point. Calls vmmMemMapInit() and then
  vmmPagingInit(). If either fails the kernel halts.

vmmMemMapInit()
  Builds the physical page frame map — a linked list of all available physical
  pages. Each entry tracks:
    - Physical frame address
    - Ownership (which process holds the page)
    - Reference count (for COW sharing)
    - Status flags (free, allocated, COW-pending)

vmmPagingInit()
  Enables hardware paging. Sets up the kernel's initial page directory,
  identity-maps the lower 1 MB, and maps the physical frame list into the
  top 1 GB so the kernel can reach it from any process context.

vmmCreateVirtualSpace(pid)
  Allocates and initializes a brand-new page directory for the process
  identified by pid. Returns the physical base address of the new page
  directory. The shared lower 1 MB and top 1 GB kernel mappings are
  pre-installed; everything between 1 MB and 3 GB starts unmapped.

vmmCopyVirtualSpace(pid)
  Forks the address space of the process identified by pid using
  copy-on-write (COW):
    1. The entire 2 MB - 3 GB range is duplicated at the page-table level.
    2. All pages in that range are marked read-only and COW-pending in both
       the parent and the child; no physical memory is copied.
    3. On the first write to any shared page a page fault fires.
    4. The page fault handler (pagefault.c) allocates a new physical frame,
       copies the content, clears the COW flag, and updates the faulting
       process's page table entry to point to the new frame.


3. Page Fault Handling
----------------------

Source: sys/vmm/page_fault.S, sys/vmm/pagefault.c

The x86 page-fault exception (interrupt 14) is routed to the VMM handler.
The handler distinguishes three cases:

  - COW fault: A write to a shared COW page. Allocate a new frame, copy,
    update PTE, and resume the faulting instruction.
  - Demand-zero: A first access to an allocated but not-yet-mapped page.
    Allocate a zeroed frame, map it, and resume.
  - Invalid access: Access to an unmapped or protected region. Deliver
    SIGSEGV to the faulting process.
